# Decisions

This file owns the decisions taken without the supervisor that are in force: the date, what was decided, why, and what it costs. A reversed decision is removed, and the entry that replaces it says what it replaced; `git log -p --follow docs/decisions.md` keeps the old text. ⛔ Not here: the stack table and the state of each choice's verification, owned by [architecture.md](architecture.md); progress, blockers and deferred work, owned by GitHub issues (milestones M3 · M4 · M5 · M6 · M7).

## 2026-09-29 — A slides citation opens its whole PDF, and a conversation is deleted outright

1. **The PDF a slides citation came from is served whole and inline to any logged-in account, keyed by its sha256, and every miss is a 404.** `GET /api/sources/<sha256>` finds the file through the parse sidecars and serves it only from inside the corpus directory, never from a path the client sends (`apps/qa/sources.py`); the source card links it at `#page=N`, so the browser's own viewer opens the cited page.
   **Why:** Open WebUI and Onyx open a cited file the same way — by id, behind authentication, in the browser's viewer (outside the repository: Open WebUI and Onyx source). An in-page viewer would ship pdf.js, whose worker alone is 374 kB gzipped, more than the whole first-load bundle. A 404 for a key the endpoint will not serve does not confirm the content exists; Onyx answers a file the caller may not read with a 404 for the same reason.
   **The price:** registration is open, so anyone who registers can download whole decks, more than the excerpts `POST /api/ask` shows. `#36` limits this endpoint to the decks of courses in the caller's programme, past editions included, which is consistency with retrieval and not protection: the programme is self-declared ([data-model.md](data-model.md), scope invariant 3). What narrows the exposure is the registration policy and the roles of `#93`. The sidecars record absolute paths, so the corpus is served only on the machine that parsed it.
2. **A student deletes a conversation outright: `DELETE /api/conversations/<id>` removes the row, and its messages go with it (`CASCADE`).** The delete and the writing of a question's two messages lock the same conversation row, so whichever comes second sees what the first committed; a question that waited in the queue while its conversation was deleted is refused with 400 before anything is written, and the answer slot is freed at once (`apps/qa/conversation_views.py`, `apps/qa/conversations.py`). There is no rename, pin, archive or soft delete.
   **Why:** Open WebUI, LibreChat, vercel/chatbot and LobeChat delete a conversation outright (outside the repository: their source). M3 reads the gold set and `data/webcorpus/decisions.jsonl`, not the `Message` table, so no evaluation depends on keeping deleted rows.
   **The price:** the incomplete answers of a deleted conversation, which the `Message` docstring calls raw material for M3's error taxonomy, go with it; every question's write takes one more row-lock query.

## 2026-09-28 — Slides points carry their edition, and a re-index replaces a source file within it

1. **`rag.parse` requires `--course` and `--academic-year` instead of inferring the course from the target directory name.** Both flags are `required=True`; `main()` checks the pair against `rag.chunk.edition_of` before touching a file and refuses through `parser.error` on a malformed one.
   **Why:** a directory name (`PPM`) is not a course code, and re-parsing by directory name would write points that match neither the delete key nor the evaluation's edition.
   **The price:** every parse spells out the edition.
2. **A re-index replaces a slides file by its source, (`source_file`, `course`, `academic_year`), and writes before it deletes.** `index_chunks` upserts a file's new points, then `replace_slides_sources` deletes every other point under that key (`rag/index.py`); the sha in `chunk_id` only says whether the content changed. Web chunks follow the same order under their (`url`, `ingest_source`) pair.
   **Why:** deleting by sha, a file whose content changed looks for its new sha and never finds the old points, so both versions stay retrievable. LangChain's indexing API names a document by `source_id_key`, and its `incremental` cleanup removes the stale versions of the sources it saw during the run (outside the repository: LangChain source, `langchain_core/indexing/api.py`). An unmerged Dify pull request, #37068, reports vectors left behind when deletion recomputed ids instead of filtering on a stable field (outside the repository). Writing first means a file is never missing from the index; a crash between the two steps leaves extra points that the next run removes.
   **The price:** one edition of one PDF has one parse variant in a collection.
3. **Indexing a directory syncs the editions it holds.** After a directory run in which no file failed, `sync_editions` deletes, for each edition the run saw, the points whose `source_file` is none of the directory's files (`rag/index.py`); two files carrying one source file of one edition count as a failed file, and a single file never deletes another. This is LangChain's `full` cleanup limited to the editions seen in the run. LangChain's cleanup is an explicit `cleanup` argument (outside the repository: LangChain source, `langchain_core/indexing/api.py`); here it is implicit, because deleted and renamed files must not stay retrievable.
   **Why:** a deck removed or renamed in the corpus directory would otherwise keep answering.
   **The price:** a directory must hold an edition's whole set of files; to update some files only, index them one by one. The run logs the files it deletes before deleting them.

## 2026-09-28 — An AD code belongs to one course, and codes and years are written in ASCII

1. **An AD code belongs to one course.** `CurriculumEntry.clean()` refuses an `ad_code` that another course's entry holds, or that is another course's `Course.code`; `Course.clean()` refuses a `code` an entry of another course holds as its `ad_code`. A course's own code, listed as its own entry's `ad_code` — PPM's TECNICO APPLICATIVO row, `ad_code="B028451"` — is not a conflict.
   **Why:** Cineca's catalogue opens one teaching per AD code, so one code cannot answer to two courses. Canvas validates its own analogue, `sis_source_id`, at the application layer — a Rails `uniqueness` validation plus a pre-save check, not a database exclusion constraint (outside the repository: Canvas LMS source). Two database-level alternatives were turned down: a dedicated `AdCode` table, since nothing reads an AD code except through its owning `CurriculumEntry` or `Course`; and a PostgreSQL exclusion constraint, which needs the `btree_gist` extension to guard rows that people enter through the admin, where `full_clean()` runs in any case.
   **The price:** `loaddata` and the ORM's `.create()` skip `clean()`, so a fixture or a script that bypasses `full_clean()` can write a conflicting AD code; only a form or a script that calls it is protected.
2. **`Course.code`, `CurriculumEntry.ad_code` and `CourseEdition.academic_year` are written in ASCII, and `year_of_study` is bounded, each by a database constraint.** The constraints are `catalog_course_code_format`, `catalog_entry_ad_code_format`, `catalog_edition_academic_year_format` and `catalog_entry_year_of_study_range` (`apps/catalog/models.py`); their character classes are the ASCII `[A-Z0-9]` and `[0-9]`, never a `\d` class, whose reach past ASCII depends on collation. The patterns and the range are owned by [data-model.md](data-model.md), scope invariant 1.
   **Why:** PostgreSQL's documentation on its character classes states that whether a non-ASCII character belongs to a class such as `\d` depends on collation, and only the `C` locale excludes every non-ASCII character from it; `[0-9]` matches the ten ASCII digits regardless of collation (outside the repository: PostgreSQL documentation, pattern matching). A trailing space or a stray `:` in a code would break `CODE:YEAR`, the string both `rag/` and the command line parse.
   **The price:** an official code printed with a character outside `[A-Z0-9]` — a hyphen, an accent — needs the constraint widened before it can be entered.

## 2026-09-28 — Commit messages are checked as they are made and across history, and history is linear

1. **A commit message is checked as the commit is made, and every commit in history on every run.** The `commit-msg` hook ([scripts/guards/commits.py](../scripts/guards/commits.py)) holds a message to the header of commitlint's config-conventional — its eleven types, at most 100 characters, no full stop, a subject that does not start with a capital letter — to English, and to no AI tool's signature. `commit-history` ([scripts/guards/history.py](../scripts/guards/history.py)) holds every commit to the same rules. It is the net for what never met the first hook — a commit made on github.com, with `--no-verify`, or pushed past the ruleset by an admin — and the reason the `hooks` job fetches the whole history. The nine commits from before these rules that break one are frozen in the module with their reasons, and an entry no commit needs any more fails the run. A message carries no `guard-ignore` marker: it has no comment syntax, and history keeps its exceptions in that list alone.
   **Why written here:** this repository tried `compilerla/conventional-pre-commit` in `9aabc1f` and dropped it seven minutes later in `da6132c`. It reads the header alone, so it cannot see a signature trailer, and it cannot read history. The pattern itself is the usual one (outside the repository): `angular/angular`, `conventional-changelog/commitlint` and `nestjs/nest` check the message in a `commit-msg` hook, and commitlint's CI guide lints a range of commits after a checkout with `fetch-depth: 0`, as `zulip/zulip` does with `tools/commit-message-lint`. One difference is deliberate: commitlint lets `fixup!`, `squash!` and `amend!` through by default (`@commitlint/is-ignored`), and history here does not, since a rebase merge would land them as they are.
2. **History is linear: pull requests land by rebase, and a merge commit is refused.** The ruleset on main requires a linear history and allows rebase merges only. Squashing would give main a commit whose header is the pull request's title, which no hook ever read; with a rebase, what the `hooks` job checked on the branch is exactly what reaches main. `git merge` is refused at the message hook, where `git merge --abort` undoes it cleanly, and the README's setup sets `pull.rebase` so that `git pull` does not merge in the first place. The five merge commits of the history are frozen with the rest.
   **The price:** the message hook starts pre-commit a second time at every commit, 0.6 to 0.9 s on the laptop (`pre-commit run --hook-stage commit-msg`), and `commit-history` adds about 0.3 s to every commit and to every run of the chain. A clone set up before this entry runs `pre-commit install` once more. Because history is read at every commit, a commit that breaks a rule stops the next one: a `fixup!` until it is squashed, and a commit that never met the message hook even for `git commit --amend`; `commit-history` in the `SKIP` environment variable (`$env:SKIP = "commit-history"` in PowerShell) gets past it, and the message hook reads the new message all the same. A bad commit that reaches main can only be frozen, never fixed, because shared history is not rewritten.

## 2026-09-28 — The pre-commit hooks are a step of the chain, and CI runs them in a job of their own

1. **`.pre-commit-config.yaml` is the one definition of the file-level checks, and the chain runs it.** The `hooks` step of [scripts/check.py](../scripts/check.py) runs every hook over every tracked file, and CI calls it from a `hooks` job that runs beside `check` rather than ahead of it, with only the dev dependency group installed. Before this, CI ran no hook at all: trailing whitespace or a malformed YAML file was caught only on a machine where `pre-commit install` had been run. The survey behind it (outside the repository): `astral-sh/ruff` runs its hooks in a job of its own with `uv run --only-dev --locked`, `getsentry/sentry` and `fastapi/fastapi` in a workflow of their own, and `pydantic/pydantic` with `pre-commit/action`; `netbox-community/netbox` instead repeats its hooks as CI steps (`ruff-action`, `makemigrations --check`), the two-copies state the 2026-09-24 entry retired.
   Four steps left the chain with it. `lint` and `format` ran ruff 0.16.7 from the venv while the hook ran 0.16.1, so a commit and CI judged the same file with two linters; ruff lives in the hook alone, out of the dev dependency group, and Dependabot's `pre-commit` ecosystem moves its `rev`. `django` was a strict subset of `deploy`, since `check --deploy` runs the ordinary system checks and adds the deployment ones; `migrations` repeated `tests/test_accounts.py`, whose `test_no_pending_migrations` is the only gate on migration drift. This settles what the 2026-09-24 entry left to the test-suite epic `#89`.
   **Why a job of its own:** the hooks need neither torch nor PostgreSQL, so beside `check` they cost no time on the path a pull request waits for; ahead of it they would. `uv-lock` is skipped inside the chain, because it resolves over the network and the `check` job's `uv sync --locked` is the same gate; a commit runs it.
   **The price:** a hook that rewrites a file (ruff, whitespace) fails the run that rewrote it, so the chain is run again after reviewing the diff. ruff is pinned by a commit SHA in the hook configuration rather than by `uv.lock`, so `pip-audit` does not see it; the SHA cannot move under the pin, as a tag could. The local chain is serial, so it pays for the hooks step itself: about 6 s on the laptop with every hook of this entry, against about 8 s for the four steps it replaced. In CI the `check` job's median over five runs is 124 s, against 125 s before this entry, and the `hooks` job's, over the same five, is 16 s, beside it; `ci.yml` caps both jobs, the tests step and the hooks step, each at about twice what was measured.
2. **Spelling is checked by typos, against a list of known misspellings, not by a dictionary.** A dictionary checker such as cspell, the tool issue `#90` first named, flags every Italian and Chinese word of a multilingual repository until each is listed; another project of the author switched cspell on and started from 6569 findings (outside the repository: `3M-Consulting/app-studio3mstp` issue 72). typos knows misspellings rather than words, so a quotation in Italian mostly passes, and it is what `astral-sh/ruff` and `astral-sh/uv` run (outside the repository). Here it reports and never rewrites, unlike its default: an Italian word that happens to be a known English misspelling would otherwise be "corrected" inside a quotation. What it leaves out is in `_typos.toml`, each entry under a comment with its reason, which `tests/test_guards.py` enforces.
   **The price:** a misspelling typos does not know passes.
3. **A rule no off-the-shelf linter knows is a guard in [scripts/guards](../scripts/guards/), proven by examples, and an exception to it is written where it applies.** Each rule carries files it must pass and files it must flag, and one test runs them all, so a rule whose pattern quietly stopped matching fails the suite instead of passing forever — the pattern of `zulip/zulip`'s `tools/tests/test_zulint_custom_rules.py` (outside the repository). An exception is a `guard-ignore <rule>: <reason>` comment on the line it silences or alone above it; a marker without a reason, naming no rule or silencing nothing is itself a finding, as Biome requires an explanation on its suppressions and ruff reports an unused `noqa` (outside the repository). A central allow-list was the alternative, and the one the checker that moved the documents to English (`#43`) kept: it sits away from the lines it excuses, so nothing says when one of them changes. The guards use the standard library alone, because pre-commit runs them in a virtualenv of their own.
   **The price:** a comment beside the exception, and one blind spot, written in the framework's docstring: a TypeScript string that spells out a `//` marker is read as one.

## 2026-09-26 — Until a database has to keep its data, each app has one migration

1. **Each app keeps a single `0001_initial.py` until the first database whose data has to be kept.** A model change rewrites that file — it is deleted and generated again — and the local database is rebuilt; nothing is added as a `0002`. From the first database that must keep its data, such as a demonstration on the MICC servers or a deployment, migrations only add, as point 5 of *The data model is decided on paper* (2026-09-25) states. This narrows that point to the time after such a database exists; its other half, that each table lands with the issue that first uses it, is unchanged.
   **Why:** a migration file carries a database that holds data from one schema to the next. With no such database there is nothing to carry, and every extra file is history nobody will replay. The files cannot go altogether: Django requires the custom user model to be created in the first migration of its app, and apps without migrations must not have relations to apps with them (outside the repository: Django 5.2 documentation, "Customizing authentication" and "Migrations"). Andrew Godwin, who wrote Django's migration framework, described squashing as meant for installs one cannot control (outside the repository: django-developers, "Do people actually squash migrations?"); with no install to control, a history protects nothing. InvenTree shows the cost of waiting: it proposed shipping its 1.0 with squashed migrations in 2023 and squashed its pre-1.0 history only at 1.6, behind a guard that stops older databases from upgrading, because by then it had installs to carry (outside the repository: InvenTree issue 5015 and pull request 12830). Point 1 of 2026-08-24, *Order of work*, counted on the same window when it switched to a custom user model while doing so was free.
   **The price:** every model change costs a local rebuild — the database volume is deleted, and whatever was saved with `dumpdata` is loaded back. The window closes the day a kept database appears, and the switch has to be remembered then: the check chain cannot tell a rewritten `0001` from a new one.

## 2026-09-25 — PPM read from Moodle and Cineca: one course, two AD codes, one edition

1. **A course's code is the AD code of the Moodle course that holds its material, and it is fixed once entered.** UniFi's Moodle opens one course per AD code and academic year; the teacher keeps the material in one of them and declares the others *mutuati*. PPM's material has been in `B028451` every academic year since 2020-2021, with `B003712` declared as its *mutuato*, so PPM's `Course.code` is `B028451`. The code does not follow a teacher who later moves the material to another container.
   **Why:** an edition names material, and the material lives in the container. Which code is the container is the teacher's choice, not a university rule: for Intelligenza Artificiale it is `B003725`, the code without a curriculum, the opposite of PPM (outside the repository: UniFi Moodle, `e-l.unifi.it`).
   **The price:** the container is read from Moodle by a person. The Cineca course catalogue lists the two AD codes as two equal teachings and has no field saying which one is *mutuata da* the other.
2. **A course appears once per curriculum; when a curriculum lists two AD codes for it, the entry takes the one listed only in that curriculum.** The Cineca study plan of `B047`, curriculum TECNICO APPLICATIVO, lists PPM under both `B003712` and `B028451`, while TECNICO SCIENTIFICO lists `B003712` alone, so PPM is two entries: TECNICO APPLICATIVO with `B028451`, TECNICO SCIENTIFICO with `B003712`. Any other case is decided by whoever enters the row. Only PPM has been checked; four more courses of the same plan come in pairs of AD codes (outside the repository: Cineca course catalogue, `unifi.coursecatalogue.cineca.it`).
   **Why:** it keeps the (`programme`, `curriculum`, `course`) constraint of [data-model.md](data-model.md), so a course has one year of study in each curriculum. Relaxing the constraint later to one row per AD code only adds rows; tightening it after the fact would first have to remove some.
   **The price:** the table does not record that a TECNICO APPLICATIVO student may also take PPM under `B003712`, a credit slot that no code reads.
3. **The curriculum is stored by the name the Cineca catalogue prints**, such as `TECNICO APPLICATIVO`, and as an empty string when it prints none. The name is an identifier, not text to translate, so it carries no `locale`.
   **Why:** Cineca owns the study plans and shows the name only; the code `E70` appears in Moodle course titles alone, and the code of TECNICO SCIENTIFICO was not found on the pages checked.
   **The price:** a misspelt name is a new curriculum, and no constraint can tell the two apart; the stored values are checked by eye.
4. **Official fields no code reads are not stored**: the programme's level (Cineca *Tipo di corso*), CFU, teaching period, mandatory or optional, cohort. Each is an additive `AddField` when a reader appears.
   **Why:** point 5 of *The data model is decided on paper*, the entry below: a column lands with the code that first uses it.
   **The price:** a cohort, if one is ever needed, changes the (`programme`, `curriculum`, `course`) constraint as well as adding a column, since a curriculum's year of study is then per cohort.
5. **The corpus is one edition.** All 31 PDFs in `data/corpus/PPM/` match, title by title, the 2025-2026 Moodle course of `B028451`. The years in their file names (2024, 2025, 2026) date the slides, not the teaching: the teacher reuses decks across academic years. This corrects `#96`, which read the file names as two academic years.
   **Why:** a file name dates the deck; the Moodle course dates the teaching.
   **The price:** the evaluation scope is a single pair, (`B028451`, `2025-2026`).

**Status:** 🔶 the tables and their constraints are `apps/catalog/models.py`; PPM's rows are entered with `#96` (M5).

## 2026-09-25 — The data model is decided on paper before roles are built on it

1. **A course has two levels and a yearly edition.** A `DegreeProgramme` (such as `B047`) lists `Course` rows (such as `B003725`) through `CurriculumEntry`, which carries `year_of_study`, the `ad_code` and the curriculum, so a course shared between programmes (*mutuazione*) is one more entry pointing at the same course, never a copy of its material. Material, syllabus, reading list and reference pages hang on a `CourseEdition` (`course`, `academic_year` such as `2025-2026`); past editions are kept and can be chosen. Which edition is current is a manual switch, `is_current`, flipped by a teacher or the secretariat, at most one per course, and a search defaults to the current edition. This reverses the course label `"PPM"`, taken from the corpus directory name: the slides payload field `course` becomes the UniFi course code, and `academic_year` joins it.
   **Why:** this is how UniFi's own Moodle lists a course — `B003725 (B047)`, the programme as its category, shared courses marked *mutuati* — and Cineca Esse3, Moodle categories and Canvas accounts nest the same way; UniFi's Moodle opens one container per academic year, as Open edX does with course runs and Canvas with terms (outside the repository). The key stays a plain string, the way Open edX keeps `CourseKey` a string that its `CourseOverview` table is keyed by (outside the repository), so `rag/` does not import Django. A switch and not a date, because a new edition is worth searching only once its material is in, and whoever uploads it knows when that is.
   **The price:** every slides point in Qdrant is rewritten to the new key, and the evaluation pins PPM's code and year instead of following `is_current`, so a switch cannot move an M3 number.
   **Status:** 🔶 the four tables and the admin are `apps/catalog/models.py`, `apps/catalog/admin.py`, and the switch is `set_current()` in `apps/catalog/editions.py`; the slides payload carries the code and year (`rag/chunk.py`), and the stored points moved to it ([experiment-log.md](experiment-log.md), entry of 2026-09-28, *The slides points move to their edition key without re-embedding*). Missing: a search defaulting to the current edition, `#36` (M5), and the switch flipped by a teacher or the secretariat, `#93` (M5).
2. **Roles are rows with a scope; permissions are code.** `RoleAssignment` (`user`, `role`, nullable `programme`, nullable `edition`) holds the staff scopes: a teacher is assigned to a `CourseEdition` and reassigned every year, the secretariat to a `DegreeProgramme`. What each role may do is a permission registry in code, and views check a permission, never a role name — the one-gate-per-action rule of `#92`. The site administrator is Django's `is_superuser`, not a role row. Where a student's programme is stored — a student row in `RoleAssignment` or a field on `User` — is left to `#93`. That programme is **a scope boundary, self-declared until `#44`**: it bounds the courses a student's search may cover, and it is not a security boundary, because the student states it.
   **Why:** one table with nullable scope columns is Open edX's `CourseAccessRole`; a role-to-permission registry in code is Sentry's; teachers per term course and staff per category are Canvas enrollments and Moodle role assignments at category level (outside the repository). A teacher is scoped to the edition and not the course because of point 1: the edition owns what a teacher edits.
   **The price:** teacher assignments are repeated every year (the secretariat copies the previous year's rows), and until `#44` brings the university identity nothing stops a student from declaring another programme.
   **Status:** 🔜 M5 `#93`.
3. **Anonymous students ask campus questions only, and nothing of theirs is stored.** Their multi-turn history lives in the browser and travels with each request; the server treats it as untrusted input and keeps no row, so `Conversation.owner` stays non-nullable and no migration follows. Course questions and stored conversations stay behind login. It replaces the rule of 2026-08-27 that made the whole site login-only.
   **Why:** that rule rested on a multi-turn conversation being per-user state; holding that state in the browser removes the reason without an ownerless row the database would have to guard. Open WebUI stores no anonymous chat, and the OpenAI Chat Completions API is stateless, the caller resending `messages` every time (outside the repository). The campus corpus is public pages, so an anonymous reader learns nothing a browser would not show.
   **The price:** the history a client sends has to be bounded and validated, and an anonymous request has to be kept out of course material explicitly, by passing `scope=[]`, which skips the slides collection (`rag/search.py`); both are checklist items of `#93`.
   **Status:** 🔜 M5 `#93`; the whole site asks for login (`config/settings.py`).
4. **Content belongs to the edition, and each kind of content has one owner.** Material uploaded by a teacher or the secretariat belongs to the `CourseEdition`; `uploaded_by` is kept for audit, which answers the uploaded-material part of `#17`; the attribution of `live` web points stays open there. Students do not upload. This reverses `#36`, where only the uploader could see a file. The syllabus is split into the five U-GOV sections (Obiettivi · Prerequisiti · Programma · Metodi didattici · Modalità di verifica); the reading list is owned by `ReadingItem` alone and is never repeated as a syllabus section. Both reach retrieval; the library catalogue (OPAC) is not connected. `WebSource` (`url`, nullable `edition`) is what should be fetched — a campus page when the edition is empty, a course reference page otherwise — and `data/webcorpus/registry.jsonl` is what was fetched; a task in `apps/` reads the first and hands `rag.crawl` plain data derived from it.
   **Why:** a workspace owning its documents with the uploader kept as a column is AnythingLLM's `workspace_documents` and Dify's `Document.created_by`; an editable source list apart from the pipeline's record is Dify's `Dataset` next to its `Document`; the section names are the ones UniFi's syllabus pages use, and a reading list as rows with title, authors and importance is Talis Aspire's (outside the repository). A course is taught to everyone enrolled in it, so its material is shared by construction.
   **The price:** a student cannot add their own notes (point 7).
   **Status:** 🔜 M5 `#35` `#97`.
5. **Migrations only add.** No table or column is dropped or renamed, and each table lands with the issue that first uses it, not ahead of it — the rule dependencies follow. The concrete order is owned by [data-model.md](data-model.md).
   **Why:** Django's "Writing migrations" guide adds a nullable field, backfills it and tightens it afterwards, and expand/contract is the general name for the pattern (outside the repository); when nothing is removed, the code of each step runs against the schema of the next.
6. **Four refinements follow from the points above.** A slides point's identity carries the course code and `academic_year`, since the same PDF in two editions would otherwise collide on `chunk_id`. Putting a student's own year first is ordering in the interface list only, never a filter. `locale` goes only on rows with user-visible text — programme and course names, `Syllabus`, `ReadingItem` — and not on `CourseMaterial`, whose language is carried by each chunk's `locale`. `year_of_study` on the student lands with the student course list of `#36`, the first code that reads it.
   **Why:** each keeps one fact in one place: an identity blind to the edition cannot tell editions apart, a year used as a filter would contradict the scope of point 2, and a file-level language would be a second copy of the chunk-level field that the corpus notes in [architecture.md](architecture.md) ask for.
   **Status:** 🔶 the slides identity is `rag/chunk.py`; the student's year is `#36` (M5).
7. **Two things are deferred, each with an owner.** Global settings — which model answers, and similar site-wide choices — wait in `#51` until the model runs on the MICC servers under `#18`; the direction noted there, a singleton row choosing from a profile list in `.env`, is a suggestion, not a decision. Student uploads visible only to their author wait in `#36`; the additive change they need is described in [data-model.md](data-model.md).
   **Why:** vLLM serves one model per process (outside the repository), so a model name an administrator could type would name a model the server does not serve; the settings are worth designing only against the server that runs them.

## 2026-09-24 — `just` is retired; scripts/check.py is the one chain

1. **The justfile is gone, and nothing replaces it as a tool.** It had 27 recipes, and CI called none of them: `.github/workflows/ci.yml` spelled every command out a second time, so the two copies drifted. Which tool holds the aggregate is secondary, and none of the projects surveyed uses `just`. A Python script needs nothing that `uv sync` does not install, and runs natively under PowerShell.

## 2026-09-15 — The palette turns achromatic, and the gate flips direction

1. **Commit `a521e6a`, "give the interface an accent colour of its own and gate it", is reverted.** It had given the interface a teal accent because `--accent` equalled `--ink` character for character and the interface had no colour of its own. After trying Morphic and Perplexity (outside the repository), their palette is adopted, and it is **fully achromatic**: chroma exactly 0 on every token except the `--warn*` family. The accent is the ink again, this time by choice.
   **The price:** the link between a citation in the answer and its source card was carried by colour, and it is this interface's most characteristic interaction. It moves to **fill** — the pill carries `--mark`, the lit card `--mark` plus an ink ring — and those are assertions in `frontend/src/features/chat/CitationList.test.tsx`, not a gate.
2. **`MIN_CHROMA` becomes `MAX_CHROMA`, and the gate is weaker.** It asked "prove you have a colour"; it asks "prove you stayed neutral". That is **not the same rigour**: with every neutral token at chroma zero, no legitimate change can make the new check fail, so it guards against oversight only. What the old check defended — "the accent is not the ink" — cannot be defended by a number and becomes an assertion on the source.
   In exchange the gate gains a **surface ladder**: the lightness distance between two fills that touch without a border, the one check under tension on an all-grey palette. It compares whole percentage points, not floating point: `0.25 - 0.23` is `0.019999999999999990`, and a naive check would fail a correct palette (`frontend/scripts/check-contrast.mjs`).
3. **Surfaces and inks are two namespaces**: a duplicate inside one is noise, a coincidence across the two is a fact of the palette. So `--accent-text` and `--mark-ink`, equal to `--ink` in both themes, are deleted, and `--accent` stays although it equals `--ink`.
4. **Tests run under `node`, and a test file asks for jsdom when it needs a document.** Under jsdom, Vite resolves with client conditions and `import.meta.url` stops being a `file:` URL, which breaks the tests that read their subject from disk (`frontend/vite.config.ts`).

## 2026-08-24 — Order of work

1. **M5 comes before M3**, up to M6's clean machine where one `docker compose up` starts everything and the browser demonstrates both knowledge bases, accounts included. Three reasons. The research results were terminal output only, and meetings and the defence need something visible. `migrate` had never run, so a custom user model and the switch to PostgreSQL cost nothing then, while a custom user model retrofitted later rewrites every migration. 2. **Qdrant moves from embedded to a service in the compose file, and the index moves whole with the client's official `migrate()`.** Once the website runs, the web process, the Celery worker and terminal evaluations all need the index, and embedded mode's single-process file lock keeps the website from starting. qdrant-client's `QdrantClient.migrate()` copies the points of both collections, vectors and payloads, so nothing is re-encoded and the pages fetched live, which exist only in the index (`rag/live.py`: "Live keeps no snapshot file"), move with the rest. It is the one supported path from local mode to a server: Qdrant's migration tool reads only from a server, and local mode has no snapshots (outside the repository: the `qdrant/migration` README; qdrant-client, `local/qdrant_local.py`). A server searches its segments in parallel and returns equal scores in no fixed order, so equal fused scores are ranked by point id, or the same question could keep a different point at the cut on each run (`rag/search.py`). Every client opens the server at `QDRANT_URL` (`config/env.py`), and an embedded index only when given its directory (`--qdrant DIR`), the way Dify reads `QDRANT_URL` (outside the repository: Dify's Qdrant vector store); an empty value is an error, never a fallback. It replaces the earlier plan of copying only the live pages with `scroll` and `upsert` and reindexing the rest.

## 2026-08-04 — Sparse retrieval is fastembed BM25 with an IDF modifier; SPLADE is not pursued
