# Decisions

This file holds the decisions taken without the supervisor that the thesis argues, and only those in force: the date, what was decided, why, and what it costs. What earns an entry, and where the reasons for every other choice go, is in [CLAUDE.md](../CLAUDE.md), documentation conventions. A reversal replaces the entry it reverses and does not narrate it; `git log -p --follow docs/decisions.md` keeps the old text. ⛔ Not here: the stack table and the state of each choice's verification, owned by [architecture.md](architecture.md); accepted security risks, owned by [security.md](security.md); progress, blockers and deferred work, owned by GitHub issues (milestones M3 · M4 · M5 · M6 · M7).

## 2026-10-08 — Text the project did not write enters every prompt as quoted material

1. **Every prompt holds the text it did not write between `<quoted>` and `</quoted>`, and says what that text is.** An excerpt, an earlier turn of the conversation, a link's anchor and a fetched page's sample go into the user message through `quote()` (`rag/llm.py`), each tag on a line of its own; what the project writes, an excerpt's number and its citation marker, stays outside. A look-alike of a tag inside the text, literal or upper-case, in a fullwidth or small form, split by an invisible character or by spaces, is found on the text's NFKC form and replaced in the original, every other character kept as it was (`neutralize()`). A URL left outside the quote, the one in a citation marker included, is percent-encoded down to what RFC 3986 allows, so it holds no space, bracket or word in another script (`inert_url()`), and a content type reaches the gate only as a media type with token parameters (`inert_content_type()`); a citation the API returns is that same marker. Every system prompt that reads such text carries one sentence saying that the quote is data and that an instruction inside it is text to report or to judge (`QUOTED_CLAUSE`). The router's prompt does not: it reads the student's own questions and nothing else. `tests/test_llm.py` finds every system message under `rag/` and fails on a prompt without the sentence, and drives each prompt with a text written to break out of its block.
   **Why:** separating external content from instructions is the mitigation OWASP names for indirect prompt injection (outside the repository: OWASP Top 10 for LLM Applications 2025, LLM01, "Segregate and identify external content"), and retrieval-augmented tools delimit what they retrieve the same way: Open WebUI wraps each source in a `<source>` tag, Anthropic's prompting guide puts each document in `<document>` tags, Qwen-Agent heads each one with its source and fences it (outside the repository: Open WebUI's `get_source_context()`, Anthropic's guide on long-context prompting, Qwen-Agent's RAG prompt). None of the three handles a closing tag the content forges itself; Spotlighting does, with a delimiter the content must not hold and that is removed when it does (outside the repository: Hines et al., "Defending Against Indirect Prompt Injection Attacks With Spotlighting", 2024, arXiv 2403.14720). An anonymous conversation's history is sent back by the browser, so the turns are quoted like any page. The tags stand on lines of their own because, written inline, Qwen3-4B copied them into an answer, and naming them in a rule made it copy them more ([experiment-log.md](experiment-log.md), 2026-10-08).
   **The price:** a delimiter lowers the odds that a 4B model obeys quoted text and does not remove them; why the rest is accepted is in [security.md](security.md), row LLM01:2026. Spotlighting's stronger form, datamarking, which interleaves a marker through every word of the quoted text, is left out: it is unmeasured on Qwen3-4B and may cost answer quality, so it is a comparison for M3 rather than a default. The deepening loop's pick declared two shortlists out of three unsuitable where the prompt before chose a link, a change no labelled set can judge. Generation results recorded before this date were produced with the prompt before it (`GENERATION_PROMPT_SHA256`, `tests/test_answer.py`).

## 2026-10-07 — The interface takes the university's blue on greys tinted toward it

1. **The palette carries one hue, the university's blue, on greys of the same hue.** `--accent` is `#004C7F`, the university website's own `--main-blue` (outside the repository: the stylesheet of www.unifi.it, read on 7 October 2026), its screen value of the institutional Pantone 301 that the visual identity manual names, C94 M58 Y18 K0 in print; the dark theme takes a lighter step of the same hue. The greys lean toward that hue at a chroma low enough to read as grey, as the website's `#F4F5F6` and `#212529` do, and `--accent-soft`, a fill tinted with the blue, marks where a reader is. The blue goes where something can be done or names the project: the primary button, the focus ring, links, the open conversation, the mark. An answer's text stays in ink; the link between a citation and its card stays on fill, the pill and the lit card in `--mark` and the card ringed in ink (asserted in `frontend/src/features/chat/CitationList.test.tsx`); `--warn*` stays for a failure and for confirming a destruction. The values are in `frontend/src/index.css`, and `frontend/scripts/check-contrast.mjs` holds them to the one hue.
   **Why:** after a thesis meeting the supervisor found the interface too bare and allowed the university's colour ([architecture.md](architecture.md), "The supervisor's constraints"); the visual identity manual's prohibition concerns the logo, not the colour (`#128`). The website gives the colour and nothing else: its blue band, uppercase navigation and square frames would make a lab tool read as an official page, which the university's trademark guidelines do not allow (outside the repository: *Linee guida per l'uso del marchio*, 1.4). Layout and richness follow the AI products the interface measures itself against, which spend their accent the same way: on what can be acted on, never on the reading.
   **The price:** blue means "act here" or "this is the project", so a blue word inside an answer would read as a link; the reading stays in ink for that reason, and the citation link stays on fill.

## 2026-10-05 — The staff pages live in the chat shell, where a course is offered is open to all staff, and the API serves only what a page reads

1. **The staff pages are a "Gestione" group in the chat's sidebar, not an area with a top bar of its own.** One layout route, `frontend/src/routes/ShellLayout.tsx`, holds the sidebar for the chat and for every `/staff/` page, so moving between them neither reloads the conversation list nor mounts a second sidebar. The group's items follow from the superuser flag, the programmes the caller may view and whether the account teaches an edition (`frontend/src/features/staff/landing.ts`, `frontend/src/auth/staff.ts`), while what a page offers to do follows from each row's `permissions`: the superuser, and secretariat staff of two programmes or more, get the list of programmes; secretariat staff of exactly one go straight to their programme; a teacher also gets their own courses. `/staff` lands on the first item.
   **Why:** the pages follow the prototype shown to the supervisor (outside the repository), whose secretariat opens on its programme. A list of one is a page with nothing to choose, so the rule carries over to staff of several programmes, rather than an item per programme, which would grow the sidebar with the scope and label each item with a programme's name. Learning platforms put the staff area in the navigation everyone uses, shown to whoever holds it: Moodle 4.0's primary navigation carries "Site administration" beside "Home", "Dashboard" and "My courses", and Canvas's global navigation an "Admin" tray listing the accounts an administrator manages (outside the repository: Moodle 4.0 release notes; Canvas guide "How do I use the Global Navigation Menu as an admin?"). A route with no path that renders its children in an `<Outlet>` is React Router's layout route (outside the repository: React Router documentation, "Routing").
   **The price:** the chat page tells the layout, through its context, when the conversations changed and which one is being answered (`frontend/src/routes/shell.ts`). Leaving a chat while it answers stops the answer: the stream is the chat page's own request, which unmounting aborts (`frontend/src/features/chat/useAsk.ts`), and any route away from the chat unmounts it, shared layout or not. The answer is kept as far as it got and marked incomplete (`Message`, `apps/qa/models.py`).
2. **Which programmes list a course is open to all staff; a programme's own plan, page and staff stay behind its scope.** `GET /api/catalog/programmes/<code>/courses` is a programme's plan, a course with no edition included. A course, wherever the API returns it — on its own, in a plan, inside an edition — carries its entries in every programme that lists it, so a teacher reads, through their edition, the names of the other programmes offering the course. A programme outside the caller's scope is a 404, its page, its plan and its secretariat alike. A course is read by whoever may view a programme that lists it (`courses_for`, `apps/roles/scopes.py`); a teacher reads no course page, and reaches their editions through their own courses.
   **Why:** the study plans are the public Cineca course catalogue (outside the repository: `unifi.coursecatalogue.cineca.it`), so hiding which programmes list a course protects nothing a browser would not show; the 404 protects what the catalogue does not publish, who holds a role where. The registry has no course scope (2026-09-29, *Staff permissions are a registry in code, answered by one backend; the admin is the superuser's*, point 1): a course is reached through a programme, and a teacher's scope is an edition.
   **The price:** every course the API returns carries its entries, read at a fixed number of queries however many there are (`tests/test_catalog_api.py`); a teacher does not see in the SPA the editions of their course they do not teach.
3. **The API serves only the reads a page makes.** The edition list has one filter, `?course=`, and a member collection (`…/teachers`, `…/secretariat`) answers `POST` alone: staff are read on their scope's own row, `teachers` on an edition and `secretariat` on a programme.
   **Why:** every endpoint resolves a scope and is tested for every caller, so one that no page calls is a surface nobody watches, and a second read of the same rows can drift from the first.
   **The price:** a reader the SPA does not have, such as a script, adds its endpoint and its tests when it appears.

## 2026-10-05 — The site is a lab site, so the interface may go as far as showcase sites, on three floors

1. **The interface may go as far as the best showcase sites: 3D, scroll-driven motion, a guided first visit.** The site is a small, non-commercial site of the MICC lab, not the university's official website, and the interface is graded (*A person confirms what automatic growth proposes; the interface is graded*, 2026-09-14, point 2). What to borrow is triaged per reference in `#135` (visuals, motion, 3D), `#136` (first visit) and `#137` (chat interaction); `#128` picks the style and the university colour.
   **Why:** a lab's demonstration site is not treated as a university service, so the interface is held to the floors of point 2 rather than to the reference of the M4 milestone alone, and the thesis gains from an interface that shows craft. The showcase sites pay for it: unseen.co loads about 7 MB first and ignores reduced motion (outside the repository: measured in YoZoLabs/airjump-website issue 42).
   **The price:** a heavier, more complex frontend; an effect that cannot pass the floors is dropped, however good it looks.
2. **Three floors hold every effect, checked by a browser job that runs in CI only (`#134`).** Nothing moves when the system asks for reduced motion; axe passes on every route in both themes; the chat's first paint stays within a byte budget, and heavy assets such as three.js load after it and are excluded by name.
   **Why:** students open the site to ask a question, often on a phone, so the question must not wait for a scene, and motion must yield to the system setting. Browser tests stay out of the local loop, which has to stay fast.
   **The price:** a Playwright job, and API fixtures kept in step with the TypeScript mirrors of the contract.

## 2026-09-29 — Staff permissions are a registry in code, answered by one backend; the admin is the superuser's

1. **Permissions are a registry in code, and one authentication backend answers them.** `apps/roles/registry.py` names five permissions, each on one kind of scope — a programme or an edition — and which role holds which. `RoleBackend` (`apps/roles/backends.py`) comes after Django's `ModelBackend` and overrides `get_user_permissions` alone, so `user.has_perm(permission, edition)`, its async twin and `get_all_permissions` give one answer. Which role covers which scope is written once, in `apps/roles/scopes.py`: a teacher covers their edition, secretariat staff every edition of every course their programme offers, and the lists and each item's `permissions` read that same resolution. An inactive account, an unknown permission, a permission of the other kind of scope and a missing object are refused; an active superuser is answered yes by Django before any backend is asked.
   **Why:** Sentry fixes its organisation roles and their scopes in code, `SENTRY_ROLES`, and openedx-authz defines its roles in code as `RoleData` (outside the repository: their source). Django's hook for per-object permissions is a backend whose permission methods take the object, the way django-guardian and django-rules plug in (outside the repository: Django 5.2 documentation, "Customizing authentication"). The ready-made options were turned down: DRF's `DjangoObjectPermissions` needs Django's model permissions, which have no scope; django-rules has no release declaring Django 5.2 support; django-guardian stores a row per object and permission, a second copy of `RoleAssignment`.
   **The price:** two authentication backends, so a `login()` that did not go through `authenticate()` names the one it uses (`RegisterView`, `apps/accounts/views.py`), and their order matters: the test client's `force_login()` records the first backend that has a `get_user()`, and only `ModelBackend`'s loads anyone.
2. **A student's programme is not a role row.** Where the programme is stored, a field on `User` or a profile of its own, is `#36`'s, the issue that first reads it.
   **Why:** a role grants something, and the programme protects nothing: it narrows a search and is self-declared. Open edX keeps a learner's enrollment, `CourseEnrollment`, apart from course staff roles, `CourseAccessRole` (outside the repository: Open edX source).
   **The price:** a second place that scopes a user, beside `RoleAssignment`.
3. **The admin admits superusers only, and `is_staff` never follows from a role.** `SuperuserAdminSite` (`config/admin.py`) is the default admin site through `config/apps.py`; a staff account that is not a superuser is sent back to the admin's login page, which says it is not authorized. The superuser enters role rows there (`apps/roles/admin.py`); staff work in the SPA, within their scope.
   **Why:** the admin edits every row of every table, so a scope cannot be drawn in it, and Django's documentation limits its recommended use to an organisation's internal management tool (outside the repository: Django 5.2 documentation, "The Django admin site", and its section on overriding the default admin site). Saleor, Sentry and Zulip do not install Django's admin at all, and their staff work in the application itself; Open edX course teams work in Studio (outside the repository: their source).
   **The price:** staff do through the site only what their pages offer (2026-10-05, *The staff pages live in the chat shell*); entering the catalogue is the superuser's job, in the admin.
4. **Switching a course's current edition needs the permission on both editions it changes.** `POST /api/catalog/editions/<id>/set-current` asks for `edition.set_current` on the new edition, and `set_current()` asks it again of the course's current edition, when there is another, inside the row lock, so the edition checked is the edition cleared (`apps/catalog/editions.py`, `apps/catalog/views.py`). A refusal for the second reason carries the code `switch_needs_both` (`apps/catalog/errors.py`) and a fixed message, which tell a page why without saying which edition is current.
   **Why:** a teacher row outlives its academic year, and the switch moves the default of the whole course, so a check on the new edition alone would let last year's teacher move the course back to their year. GitHub asks the same of a transfer, which changes two repositories: "you must have write access to the repository the issue is in and the repository you're transferring the issue to" (outside the repository: GitHub documentation, "Transferring an issue to another repository").
   **The price:** a teacher's first edition is made current by the secretariat, not by the teacher. A course offered by two programmes can be switched by either programme's secretariat, which moves the default for the other programme's students too; the course belongs to both, and a switch is undone by switching back.
5. **An assign table decides who grants what.** `GRANT_PERMISSION` (`apps/roles/registry.py`) names the permission that grants each role on its scope: secretariat staff assign teachers in their programme's editions, and no role holds the permission that assigns secretariat staff, so only the superuser does. Staff are granted and revoked under their scope (`apps/catalog/staff_views.py`) and read on their scope's own row (2026-10-05, *The staff pages live in the chat shell*, point 3), the scope resolved before the permission and the permission before the request body; each grant and revocation made there writes one line to the `apps.roles.grants` log once it commits, while the superuser's changes in the admin stay in the admin's own history, and the demo seed, `manage.py populate_demo` (`apps/roles/management/commands/populate_demo.py`), which touches `demo-` accounts only, prints each role row it adds or removes.
   **Why:** Moodle decides who may assign which role with `role_allow_assign` and fires a `role_assigned` event on each assignment, and Open edX checks the caller's authority on the course before changing its staff, in `_check_caller_authority` (outside the repository: their source). The subset rule of Saleor, Sentry and Canvas — grant only what you hold — would stop secretariat staff from assigning teachers once `#97` gives teachers a permission of their own. GitLab and Canvas nest members under their scope, `/projects/:id/members` and `/courses/:id/enrollments` (outside the repository: their API documentation).
   **The price:** secretariat staff can make themselves a teacher of an edition in their programme, which grants nothing they lack until `#97`, and the teacher row outlives their secretariat row, so revoking a person is done in the admin by username. An unknown username is a 400, which staff holding the assign permission can use to test whether an account exists, and the catalogue endpoints carry no throttle of their own.

## 2026-09-29 — A slides citation opens its whole PDF, and a conversation is deleted outright

1. **The PDF a slides citation came from is served whole and inline to any logged-in account, keyed by its sha256, and every miss is a 404.** `GET /api/sources/<sha256>` finds the file through the parse sidecars and serves it only from inside the corpus directory, never from a path the client sends (`apps/qa/sources.py`); the source card links it at `#page=N`, so the browser's own viewer opens the cited page.
   **Why:** Open WebUI and Onyx open a cited file the same way — by id, behind authentication, in the browser's viewer (outside the repository: Open WebUI and Onyx source). An in-page viewer would ship pdf.js, whose worker alone is 374 kB gzipped, more than the whole first-load bundle. A 404 for a key the endpoint will not serve does not confirm the content exists; Onyx answers a file the caller may not read with a 404 for the same reason.
   **The price:** registration is open, so anyone who registers can download whole decks, more than the excerpts `POST /api/ask` shows. `#36` limits this endpoint to the decks of courses in the caller's programme, past editions included, which is consistency with retrieval and not protection: the programme is self-declared ([data-model.md](data-model.md), scope invariant 3). What narrows the exposure is the registration policy and the roles of `#93`. The sidecars record absolute paths, so the corpus is served only on the machine that parsed it.
2. **A student deletes a conversation outright: `DELETE /api/conversations/<id>` removes the row, and its messages go with it (`CASCADE`).** The delete and the writing of a question's two messages lock the same conversation row, so whichever comes second sees what the first committed; a question that waited in the queue while its conversation was deleted is refused with 400 before anything is written, and the answer slot is freed at once (`apps/qa/conversation_views.py`, `apps/qa/conversations.py`). There is no rename, pin, archive or soft delete.
   **Why:** Open WebUI, LibreChat, vercel/chatbot and LobeChat delete a conversation outright (outside the repository: their source). M3 reads the gold set and `data/webcorpus/decisions.jsonl`, not the `Message` table, so no evaluation depends on keeping deleted rows.
   **The price:** the incomplete answers of a deleted conversation, which the `Message` docstring calls raw material for M3's error taxonomy, go with it; every question's write takes one more row-lock query.

## 2026-09-28 — Slides points carry their edition, and a re-index replaces a source file within it

1. **`rag.parse` requires `--course` and `--academic-year` instead of inferring the course from the target directory name.** Both flags are `required=True`; `main()` checks the pair against `rag.chunk.edition_of` before touching a file and refuses through `parser.error` on a malformed one.
   **Why:** a directory name (`PPM`) is not a course code, and re-parsing by directory name would write points that match neither the delete key nor the evaluation's edition.
   **The price:** every parse spells out the edition.
2. **A re-index replaces a slides file by its source, (`source_file`, `course`, `academic_year`), and writes before it deletes.** `index_chunks` upserts a file's new points, then `replace_slides_sources` deletes every other point under that key (`rag/index.py`); the sha in `chunk_id` only says whether the content changed. Web chunks follow the same order under their (`url`, `ingest_source`) pair.
   **Why:** deleting by sha, a file whose content changed looks for its new sha and never finds the old points, so both versions stay retrievable. LangChain's indexing API names a document by `source_id_key`, and its `incremental` cleanup removes the stale versions of the sources it saw during the run (outside the repository: LangChain source, `langchain_core/indexing/api.py`). An unmerged Dify pull request, #37068, reports vectors left behind when deletion recomputed ids instead of filtering on a stable field (outside the repository). Writing first means a file is never missing from the index; a crash between the two steps leaves extra points that the next run removes.
   **The price:** one edition of one PDF has one parse variant in a collection.
3. **Indexing a directory syncs the editions it holds.** After a directory run in which no file failed, `sync_editions` deletes, for each edition the run saw, the points whose `source_file` is none of the directory's files (`rag/index.py`); two files carrying one source file of one edition count as a failed file, and a single file never deletes another. This is LangChain's `full` cleanup limited to the editions seen in the run. LangChain's cleanup is an explicit `cleanup` argument (outside the repository: LangChain source, `langchain_core/indexing/api.py`); here it is implicit, because deleted and renamed files must not stay retrievable.
   **Why:** a deck removed or renamed in the corpus directory would otherwise keep answering.
   **The price:** a directory must hold an edition's whole set of files; to update some files only, index them one by one. The run logs the files it deletes before deleting them.

## 2026-09-28 — An AD code belongs to one course, and codes and years are written in ASCII

1. **An AD code belongs to one course.** `CurriculumEntry.clean()` refuses an `ad_code` that another course's entry holds, or that is another course's `Course.code`; `Course.clean()` refuses a `code` an entry of another course holds as its `ad_code`. A course's own code, listed as its own entry's `ad_code` — PPM's TECNICO APPLICATIVO row, `ad_code="B028451"` — is not a conflict.
   **Why:** Cineca's catalogue opens one teaching per AD code, so one code cannot answer to two courses. Canvas validates its own analogue, `sis_source_id`, at the application layer — a Rails `uniqueness` validation plus a pre-save check, not a database exclusion constraint (outside the repository: Canvas LMS source). Two database-level alternatives were turned down: a dedicated `AdCode` table, since nothing reads an AD code except through its owning `CurriculumEntry` or `Course`; and a PostgreSQL exclusion constraint, which needs the `btree_gist` extension to guard rows that people enter through the admin, where `full_clean()` runs in any case.
   **The price:** `loaddata` and the ORM's `.create()` skip `clean()`, so a fixture or a script that bypasses `full_clean()` can write a conflicting AD code; only a form or a script that calls it is protected.
2. **`Course.code`, `CurriculumEntry.ad_code` and `CourseEdition.academic_year` are written in ASCII, and `year_of_study` is bounded, each by a database constraint.** The constraints are `catalog_course_code_format`, `catalog_entry_ad_code_format`, `catalog_edition_academic_year_format` and `catalog_entry_year_of_study_range` (`apps/catalog/models.py`); their character classes are the ASCII `[A-Z0-9]` and `[0-9]`, never a `\d` class, whose reach past ASCII depends on collation. The patterns and the range are owned by [data-model.md](data-model.md), scope invariant 1.
   **Why:** PostgreSQL's documentation on its character classes states that whether a non-ASCII character belongs to a class such as `\d` depends on collation, and only the `C` locale excludes every non-ASCII character from it; `[0-9]` matches the ten ASCII digits regardless of collation (outside the repository: PostgreSQL documentation, pattern matching). A trailing space or a stray `:` in a code would break `CODE:YEAR`, the string both `rag/` and the command line parse.
   **The price:** an official code printed with a character outside `[A-Z0-9]` — a hyphen, an accent — needs the constraint widened before it can be entered.

## 2026-09-25 — PPM read from Moodle and Cineca: one course, two AD codes, one edition

1. **A course's code is the AD code of the Moodle course that holds its material, and it is fixed once entered.** UniFi's Moodle opens one course per AD code and academic year; the teacher keeps the material in one of them and declares the others *mutuati*. PPM's material has been in `B028451` every academic year since 2020-2021, with `B003712` declared as its *mutuato*, so PPM's `Course.code` is `B028451`. The code does not follow a teacher who later moves the material to another container.
   **Why:** an edition names material, and the material lives in the container. Which code is the container is the teacher's choice, not a university rule: for Intelligenza Artificiale it is `B003725`, the code without a curriculum, the opposite of PPM (outside the repository: UniFi Moodle, `e-l.unifi.it`).
   **The price:** the container is read from Moodle by a person. The Cineca course catalogue lists the two AD codes as two equal teachings and has no field saying which one is *mutuata da* the other.
2. **A course appears once per curriculum; when a curriculum lists two AD codes for it, the entry takes the one listed only in that curriculum.** The Cineca study plan of `B047`, curriculum TECNICO APPLICATIVO, lists PPM under both `B003712` and `B028451`, while TECNICO SCIENTIFICO lists `B003712` alone, so PPM is two entries: TECNICO APPLICATIVO with `B028451`, TECNICO SCIENTIFICO with `B003712`. Any other case is decided by whoever enters the row. Only PPM has been checked; four more courses of the same plan come in pairs of AD codes (outside the repository: Cineca course catalogue, `unifi.coursecatalogue.cineca.it`).
   **Why:** it keeps the (`programme`, `curriculum`, `course`) constraint of [data-model.md](data-model.md), so a course has one year of study in each curriculum. Relaxing the constraint later to one row per AD code only adds rows; tightening it after the fact would first have to remove some.
   **The price:** the table does not record that a TECNICO APPLICATIVO student may also take PPM under `B003712`, a credit slot that no code reads.
3. **The curriculum is stored by the name the Cineca catalogue prints**, such as `TECNICO APPLICATIVO`, and as an empty string when it prints none. The name is an identifier, not text to translate, so it carries no `locale`.
   **Why:** Cineca owns the study plans and shows the name only; the code `E70` appears in Moodle course titles alone, and the code of TECNICO SCIENTIFICO was not found on the pages checked.
   **The price:** a misspelt name is a new curriculum, and no constraint can tell the two apart; the stored values are checked by eye.
4. **Official fields no code reads are not stored**: the programme's level (Cineca *Tipo di corso*), CFU, teaching period, mandatory or optional, cohort. Each is an additive `AddField` when a reader appears.
   **Why:** point 5 of *The data model is decided on paper*, the entry below: a column lands with the code that first uses it.
   **The price:** a cohort, if one is ever needed, changes the (`programme`, `curriculum`, `course`) constraint as well as adding a column, since a curriculum's year of study is then per cohort.
5. **The corpus is one edition.** All 31 PDFs in `data/corpus/PPM/` match, title by title, the 2025-2026 Moodle course of `B028451`. The years in their file names (2024, 2025, 2026) date the slides, not the teaching: the teacher reuses decks across academic years.
   **Why:** a file name dates the deck; the Moodle course dates the teaching.
   **The price:** the evaluation scope is a single pair, (`B028451`, `2025-2026`).
6. **A course whose material no single Moodle course holds takes the code its curricula list, and says so.** For an integrated course (C.I.), such as `B047`'s `B003271` GEOMETRIA E ALGEBRA LINEARE/CALCOLO NUMERICO C.I., point 1 has no container to read, so `Course.code` is the AD code the Cineca study plan lists and `Course.code_source` is `cineca-only`; every other course is `moodle`, the default.
   **Why:** the staff pages print a course's code beside its name, and a reader who looks a `cineca-only` code up in Moodle finds no course; the page says where the code comes from instead. The field names the code's source, not the kind of course, so it is two values rather than an `is_integrated` flag: point 1 is the rule, this the one exception to it.
   **The price:** like point 1, the source is read by a person when the row is entered; the demo data file marks its integrated courses by hand (`apps/roles/management/commands/demo_catalog.json`).

**Status:** 🔶 the tables and their constraints are `apps/catalog/models.py`; PPM's rows are entered with `#96` (M5).

## 2026-09-25 — The data model is decided on paper before roles are built on it

1. **A course has two levels and a yearly edition.** A `DegreeProgramme` (such as `B047`) lists `Course` rows (such as `B003725`) through `CurriculumEntry`, which carries `year_of_study`, the `ad_code` and the curriculum, so a course shared between programmes (*mutuazione*) is one more entry pointing at the same course, never a copy of its material. Material, syllabus, reading list and reference pages hang on a `CourseEdition` (`course`, `academic_year` such as `2025-2026`); past editions are kept and can be chosen. Which edition is current is a manual switch, `is_current`, flipped by a teacher or the secretariat, at most one per course, and a search defaults to the current edition. The slides payload field `course` is the UniFi course code, and `academic_year` sits beside it.
   **Why:** this is how UniFi's own Moodle lists a course — `B003725 (B047)`, the programme as its category, shared courses marked *mutuati* — and Cineca Esse3, Moodle categories and Canvas accounts nest the same way; UniFi's Moodle opens one container per academic year, as Open edX does with course runs and Canvas with terms (outside the repository). The key stays a plain string, the way Open edX keeps `CourseKey` a string that its `CourseOverview` table is keyed by (outside the repository), so `rag/` does not import Django. A switch and not a date, because a new edition is worth searching only once its material is in, and whoever uploads it knows when that is.
   **The price:** the evaluation pins PPM's code and year instead of following `is_current`, so a switch cannot move an M3 number.
   **Status:** 🔶 the four tables and the admin are `apps/catalog/models.py`, `apps/catalog/admin.py`, and the switch is `set_current()` in `apps/catalog/editions.py`; the slides payload carries the code and year (`rag/chunk.py`), and the stored points moved to it ([experiment-log.md](experiment-log.md), entry of 2026-09-28, *The slides points move to their edition key without re-embedding*). A teacher or the secretariat flips the switch through `apps/catalog/views.py`. Missing: a search defaulting to the current edition, `#36` (M5).
2. **Roles are rows with a scope; permissions are code.** `RoleAssignment` (`user`, `role`, nullable `programme`, nullable `edition`) holds the staff scopes: a teacher is assigned to a `CourseEdition` and reassigned every year, the secretariat to a `DegreeProgramme`. What each role may do is a permission registry in code, and views check a permission, never a role name — the one-gate-per-action rule of `#92`. The site administrator is Django's `is_superuser`, not a role row. A student's programme is not a role row, and where it is stored is `#36`'s (2026-09-29, *Staff permissions are a registry in code, answered by one backend*, point 2). That programme is **a scope boundary, self-declared until `#44`**: it bounds the courses a student's search may cover, and it is not a security boundary, because the student states it.
   **Why:** one table with nullable scope columns is Open edX's `CourseAccessRole`; a role-to-permission registry in code is Sentry's; teachers per term course and staff per category are Canvas enrollments and Moodle role assignments at category level (outside the repository). A teacher is scoped to the edition and not the course because of point 1: the edition owns what a teacher edits.
   **The price:** teacher assignments are repeated every year (the secretariat copies the previous year's rows), and until `#44` brings the university identity nothing stops a student from declaring another programme.
   **Status:** 🔶 `RoleAssignment`, the registry and the backend that answers it are `apps/roles/`; copying the previous year's teacher rows is `#93` (M5).
3. **Anonymous students ask campus questions only, and nothing of theirs is stored.** Their multi-turn history lives in the browser and travels with each request; the server treats it as untrusted input and keeps no row, so `Conversation.owner` stays non-nullable and no migration follows. Course questions and stored conversations stay behind login.
   **Why:** a multi-turn conversation is per-user state only while the server holds it; held in the browser, it needs no ownerless row the database would have to guard. Open WebUI stores no anonymous chat, and the OpenAI Chat Completions API is stateless, the caller resending `messages` every time (outside the repository). The campus corpus is public pages, so an anonymous reader learns nothing a browser would not show.
   **The price:** the history a client sends has to be bounded and validated, and an anonymous request has to be kept out of course material explicitly, by passing `scope=[]`, which skips the slides collection (`rag/search.py`); both are checklist items of `#93`.
   **Status:** 🔜 M5 `#93`; the whole site asks for login (`config/settings.py`).
4. **Content belongs to the edition, and each kind of content has one owner.** Material uploaded by a teacher or the secretariat belongs to the `CourseEdition`; `uploaded_by` is kept for audit, which answers the uploaded-material part of `#17`; the attribution of `live` web points stays open there. Students do not upload. The syllabus is split into the five U-GOV sections (Obiettivi · Prerequisiti · Programma · Metodi didattici · Modalità di verifica); the reading list is owned by `ReadingItem` alone and is never repeated as a syllabus section. Both reach retrieval; the library catalogue (OPAC) is not connected. `WebSource` (`url`, nullable `edition`) is what should be fetched — a campus page when the edition is empty, a course reference page otherwise — and `data/webcorpus/registry.jsonl` is what was fetched; a task in `apps/` reads the first and hands `rag.crawl` plain data derived from it.
   **Why:** a workspace owning its documents with the uploader kept as a column is AnythingLLM's `workspace_documents` and Dify's `Document.created_by`; an editable source list apart from the pipeline's record is Dify's `Dataset` next to its `Document`; the section names are the ones UniFi's syllabus pages use, and a reading list as rows with title, authors and importance is Talis Aspire's (outside the repository). A course is taught to everyone enrolled in it, so its material is shared by construction.
   **The price:** a student cannot add their own notes (point 7).
   **Status:** 🔜 M5 `#35` `#97`.
5. **Once a database has to keep its data, migrations only add.** No table or column is dropped or renamed, and each table lands with the issue that first uses it, not ahead of it — the rule dependencies follow. The concrete order is owned by [data-model.md](data-model.md). Until the first such database — a demonstration on the MICC servers, a deployment — each app keeps one `0001_initial.py`, rewritten on every model change ([development.md](development.md)).
   **Why:** Django's "Writing migrations" guide adds a nullable field, backfills it and tightens it afterwards, and expand/contract is the general name for the pattern (outside the repository); when nothing is removed, the code of each step runs against the schema of the next. A migration file carries a database that holds data from one schema to the next, so with no such database there is nothing to carry, and every extra file is history nobody will replay. The files cannot go altogether: Django requires the custom user model to be created in the first migration of its app (outside the repository: Django 5.2 documentation, "Customizing authentication").
   **The price:** until then every model change costs a local rebuild, and the switch has to be remembered the day a kept database appears: the check chain cannot tell a rewritten `0001` from a new one.
6. **Four refinements follow from the points above.** A slides point's identity carries the course code and `academic_year`, since the same PDF in two editions would otherwise collide on `chunk_id`. Putting a student's own year first is ordering in the interface list only, never a filter. `locale` goes only on rows with user-visible text — programme and course names, `Syllabus`, `ReadingItem` — and not on `CourseMaterial`, whose language is carried by each chunk's `locale`. `year_of_study` on the student lands with the student course list of `#36`, the first code that reads it.
   **Why:** each keeps one fact in one place: an identity blind to the edition cannot tell editions apart, a year used as a filter would contradict the scope of point 2, and a file-level language would be a second copy of the chunk-level field that the corpus notes in [architecture.md](architecture.md) ask for.
   **Status:** 🔶 the slides identity is `rag/chunk.py`; the student's year is `#36` (M5).
7. **Two things are deferred, each with an owner.** Global settings — which model answers, and similar site-wide choices — wait in `#51` until the model runs on the MICC servers under `#18`; the direction noted there, a singleton row choosing from a profile list in `.env`, is a suggestion, not a decision. Student uploads visible only to their author wait in `#36`; the additive change they need is described in [data-model.md](data-model.md).
   **Why:** vLLM serves one model per process (outside the repository), so a model name an administrator could type would name a model the server does not serve; the settings are worth designing only against the server that runs them.

## 2026-08-24 — Qdrant runs as a service, and the index moves to it whole with the client's `migrate()`

1. **Qdrant moves from embedded to a service in the compose file, and the index moves whole with the client's official `migrate()`; every M3 baseline is measured on the service.** Once the website runs, the web process, the Celery worker and terminal evaluations all need the index, and embedded mode's single-process file lock keeps the website from starting. qdrant-client's `QdrantClient.migrate()` copies the points of both collections, vectors and payloads, so nothing is re-encoded and the pages fetched live, which exist only in the index (`rag/live.py`: "Live keeps no snapshot file"), move with the rest. It is the one supported path from local mode to a server: Qdrant's migration tool reads only from a server, and local mode has no snapshots (outside the repository: the `qdrant/migration` README; qdrant-client, `local/qdrant_local.py`). What `migrate()` does not carry over is set on the server afterwards: local mode reports placeholder index settings, which would keep the server from ever building an HNSW index for `unifi_web`, so each collection is set to the configuration the server gives a collection that `ensure_collection` creates; and local mode keeps no payload index, so the keyword indexes on the filtered fields are created (`rag/index.py`). A server searches its segments in parallel and returns equal scores in no fixed order, so equal fused scores are ranked by point id, or the same question could keep a different point at the cut on each run (`rag/search.py`). Every client opens the server at `QDRANT_URL` (`config/env.py`), and an embedded index only when given its directory (`--qdrant DIR`), the way Dify reads `QDRANT_URL` (outside the repository: Dify's Qdrant vector store); an empty value is an error, never a fallback.
   **Why the baselines wait for it:** the retrieval backend changes once, so no M3 number straddles two backends.
   **Status:** ✅ `docker-compose.yml`, `rag/index.py`; the move is in [experiment-log.md](experiment-log.md), entry of 2026-09-29.

## 2026-08-04 — Sparse retrieval is fastembed BM25 with an IDF modifier; SPLADE is not pursued

1. **The sparse vector is fastembed's `Qdrant/bm25`: term frequency on the document side, with IDF applied by the collection (`modifier=IDF`).** Stemming is fastembed's default English scheme. The chunk keeps `text`, the sparse input, apart from `embed_text`, the dense input with the heading chain, so the two inputs do not contaminate each other. SPLADE and a self-built IDF are not pursued.
   **Why:** the commit that settled it (`4e05db6`) records no comparison; what the choice rests on is visible in the code. BM25 adds no second neural model to the ingest and query paths, and an IDF that Qdrant computes follows the collection as points are added, live ones included, with no re-encoding.
   **The price:** Italian and Chinese chunks are tokenised and stemmed as English, so the sparse side is weakest for them; the BM25 · dense · hybrid comparison of `#25` (M3) measures what that costs.
   **Status:** ✅ `rag/index.py`.
